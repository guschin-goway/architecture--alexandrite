# Планирование: анализ, идентификация проблем и поиск решений

## 1. Анализ текущей архитектуры и процессов

### 1.1. Выявленные проблемы

**Проблема 1 - Узкое место в MES: долгий расчёт стоимости (2–30 минут).**
MES блочит обработку заказов, очередь запросов растёт, SLA API не выдерживает, партнёры теряют заказы.

**Проблема 2 - Отсутствие горизонтального масштабирования.**
Каждый сервис (онлайн-магазин, CRM, MES) работает в виде единственного EC2-инстанса, что создаёт:

  * невозможность масштабировать нагрузки,
  * невозможность наращивания параллельных расчётов стоимости,
  * Единая точка отказа.

**Проблема 3 - Отсутствие оптимизации БД и индексов.**
Жалобы операторов MES на долгую загрузку дашборда указывают на:

* неоптимальные запросы,
* отсутствие индексов по статусам и датам,
* отсутствие кэширования списка последних заказов.

**Проблема 4 - RabbitMQ как единая точка перегрузки.**
Рост заказов > очередь сообщений растёт > задержки в доставке > несвоевременное создание заказов в CRM.

**Проблема 5 - Неуправляемый API для партнёров.**
Партнёры могут отправлять неограниченное количество запросов. Нет:

* rate limiting,
* квот,
* ограничений по сложности моделей.

**Проблема 6 - Нет надежного мониторинга и алёртов.**
Нет наблюдаемости по:

* очередям RabbitMQ,
* времени расчёта моделей,
* нагрузке на базы данных,
* SLA API,
* скорости обработки заказов.

**Проблема 7 - Релизы тормозятся ручным тестированием.**
QA ручной > задержки до месяца > невозможность быстро выкатывать фиксы.

**Проблема 8 - Монофункциональные сервисы без разделения ответственности.**
MES отвечает одновременно за:

* расчёт стоимости,
* задачу производства,
* управление операторами.
  Расчёты блокируют бизнес-процессы.

**Проблема 9 - Отсутствие retry/идемпотентности API.**
Партнёры "теряют" заказы из-за неидемпотентных запросов и отсутствия корректного подтверждения.

**Проблема 10 - Отсутствие сквозной трассировки статусов заказа.**
Нет единого механизма отслеживания:

* где застрял заказ,
* когда обновлялся статус,
* какой сервис виноват.

## 2.1. Список инициатив

### Высокоприоритетные (архитектура и надёжность) - 3 ШТ.

1. **Внедрить систему мониторинга и алёртов.**
2. **Вынести расчёт стоимости из MES в отдельный сервис Cost Calculation Service.**
3. **Добавить горизонтальное масштабирование всех сервисов (автоскейлинг EC2 или Kubernetes).**
4. **Оптимизация БД MES: индексы, кэширование, read replica.**

## 2.2 Приоритизация и аргументы

#### **1. Внедрить полноценный мониторинг и алёртинг**
Почему:
* мониторинг даёт общую картину и позволяет измерить эффект остальных инициатив,
* показывает реальную загрузку API, БД, очередей и сервисов,
* позволяет фиксировать SLA, время расчёта моделей, перегрузки RabbitMQ,
* создаёт основу для обоснования изменений: до/после,
* повышает прозрачность и стабильность всей платформы.

Что делаем:
* установка Prometheus + Grafana,
* сбор метрик сервисов: время ответа, CPU, ошибки, SLA,
* сбор метрик RabbitMQ: длина очередей, скорость обработки,
* сбор метрик БД: slow queries, нагрузка master/replica,
* алёрты по SLA < 99%, переполнению очередей, росту задержек API,
* дашборды по ключевым процессам: расчёт стоимости, скорость создания заказов, загрузка операторов.

Результат:
* появляется прозрачная картина работы всей платформы,
* легко увидеть, где именно возникают проблемы,
* все будущие изменения можно измерить и доказать их пользу,
* ускоряется реакция на сбои и их устранение,
* растёт общая надёжность системы.

#### **2. Вынести расчёт стоимости в отдельный сервис (Cost Calculation Service)**

Почему:

* самое узкое место всей архитектуры,
* расчёт - CPU: должен масштабироваться отдельно,
* позволит MES работать быстро и не зависеть от расчётов,
* позволит настроить очередь задач по сложности моделей.

Результат:
* время отклика API падает,
* стабильность системы растёт,
* партнёры перестают "терять" заказы.

#### **3. Горизонтальное масштабирование всех сервисов**

Почему:

* один инстанс на сервис - критическая уязвимость,
* невозможно обслужить рост заказов,
* критично для обработки очередей.

Результат:

* система выдерживает рост нагрузки,
* исчезают задержки реакций сервисов.

#### **4. Оптимизация БД MES: индексы, кэширование, read replica**

Почему:

* текущие запросы к базе - основная причина задержек в работе MES,
* таблицы быстро растут, индексы устарели или отсутствуют,
* сложные JOIN-запросы замедляют API и UI,
* нет кэширования часто используемых данных,
* вся нагрузка (чтения/записи) выполняется одним экземпляром БД.

Что делаем:

* аудит "тяжёлых" запросов (query plan, pg_stat_statements),
* добавление недостающих индексов и пересборка действующих,
* внедрение Redis-кэша для частых запросов:
  * справочники,
  * статусы заказов,
  * настройки расчёта стоимости,
* перенос всех операций чтения на **read replica**,
* разграничение нагрузки: master - запись, replica - чтения.

Результат:

* время выполнения тяжёлых запросов сокращается в 2–10 раз,
* нагрузка на master снижается на 40–60%,
* ускорение API MES и интерфейса без изменения бизнес-логики,
* система выдерживает пиковые нагрузки без деградации,
* повышается отказоустойчивость за счёт реплики.

## 3. Видение целевой архитектуры через 6 месяцев

### Ключевые характеристики:

* Микросервис расчёта стоимости работает независимо и масштабируется по CPU.
* MES разгружен от тяжёлых вычислений, стал чистым приложением про производство.
* Все сервисы работают в режиме автоскейлинга.
* RabbitMQ стабилен, мониторится, очереди разделены по приоритетам.
* API партнёров защищён rate limiting.
* БД оптимизированы, есть read replica для аналитики и дашбордов.
* Появилась система мониторинга и алёртов.
* Снижены задержки релизов благодаря автоматизации QA.
