# Архитектурное решение по логированию

## 1. Мотивация

Симптомы текущей ситуации:

* инциденты разбираются по словам пользователей;
* долгое время расследования (high MTTR);
* отсутствие структурированных логов и единых полей (order_id, trace_id);
* мало автоматического обнаружения аномалий.

**Зачем нужно централизованное логирование:**

1. **Сократить время на расследование** - инженеры и поддержка получают все релевантные события в одной системе, с фильтрацией по order_id / trace_id / partner_id.
2. **Повысить качество поддержки** - уменьшить число ручных запросов к пользователю, быстро восстановить состояние заказа.
3. **Обеспечить соответствие и аудит** - хранение событий в течение срока, необходимого для бизнес‑ и регуляторных целей.
4. **Автоматизация оповещений и обнаружение аномалий** - раннее обнаружение DDoS, всплесков ошибок, роста DLQ.
5. **Фундамент для трассинга и метрик** - логи связываются с trace_id и дают дополнительные данные, которые не всегда попадают в спаны.

**Ожидаемые метрики, которые улучшатся:**
* MTTR (время восстановления) - снижение;
* MTTD (время обнаружения) - снижение;
* количество обращений в службу поддержки по одним и тем же инцидентам - снижение;
* время обработки одного заказа support/dev - снижение;
* % автоматических алертов (правильных) - рост.

## 2. Области покрытия и приоритеты:

Приоритет внедрения :

**Приоритет 1:**

* **RabbitMQ (broker)** - публикации/подписки, DLQ, ошибки доставки.
* **MES (backend and workers)** - все шаги расчёта стоимости.
* **Онлайн‑магазин (backend)** - создание заказа (INITIATED → SUBMITTED), загрузка файлов.

**Почему:** эти компоненты напрямую влияют на потерю заказов и жалобы партнёров/клиентов.

**Приоритет 2:**

* **CRM (backend)** - создание/обновление статусов, интеграция с MES.
* **API Gateway / API для партнёров** - входящие запросы, ошибки авторизации.

**Приоритет 3:**

* **Frontend (shop + CRM + MES SPA)** - пользовательские события, ошибки JS.

## 4. Предлагаемое решение: архитектура логирования и стек технологий

### Рекомендованный стек

* **Log ingestion & storage:** Loki как дополнение для быстрых логов от приложений и хранения больших объёмов без полного индексирования текста.
* **Log agents:** Filebeat / Fluentd / Vector - агент на хостах/контейнерах для отправки логов в Loki.
* **Structured logging libraries:** SLF4J + Logstash encoder (Java), Serilog (C#), pino/winston (Node/JS) - все должны писать JSON с обязательными полями.
* **Search & visualization:** Kibana (для ELK) или OpenSearch Dashboards / Grafana с Loki.
* **Alerting & Anomaly detection:** Prometheus Alertmanager - для обнаружения всплесков.

### Компоненты и связи

* **Интеграция с трейсингом:** все логи содержат `trace_id` и `order_id` для корреляции.
* **Alerting:** OpenSearch Alerts / ElastAlert → TG (Max) / Task-трекер.

## 5. Политика безопасности и доступ к логам

### Доступ и аутентификация

* Zero trust
* Доступ к UI (Kibana/OpenSearch Dashboard/Grafana) - через SSO/LDAP
* RBAC: группы - Support (ограниченный доступ, только просмотр), Dev (read + create dashboard), DevOps (manage indices, ILM), Security/Compliance (audit access)

### Маскирование и фильтрация

* На этапе ingestion выполнить маскирование полей (email, phone, и другие чувствительные данные). Хранить только `order_id`, `user_id_hash`.
* Логи уровня DEBUG не должны содержать увствительные данные.

### Шифрование и передача

* TLS на всех соединениях (agents → pipeline → storage)

### Аудит и retention
* Вести журнал доступа к логам и actions. Хранить audit logs отдельно 1 год.

---

## 6. Политика хранения логов

### Индексация и размеры

* Создавать отдельные индекс‑шаблоны по сервисам/типа логов, например:

    * `logs-shop-YYYY.MM.DD`
    * `logs-mes-YYYY.MM.DD`
    * `logs-rabbitmq-YYYY.MM.DD`
    * `logs-security-YYYY.MM.DD`

### Retention

* **Критические/важные компоненты:** хранить 90 дней.
* **Менее важные сервисы:** хранить 30 дней.
* **Audit logs:** хранить 365 дней.

### Архивация
* Архивировать старые логи в object storage (S3) с возможностью восстановления по запросу.
