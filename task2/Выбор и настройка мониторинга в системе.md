# Выбор и настройка мониторинга в системе

## 1. Мотивация

С ростом нагрузки, подключением API‑партнёров и увеличением количества жалоб стало очевидно, что текущей наблюдаемости в системе недостаточно. Сейчас бизнес не видит:

* почему теряются заказы;
* где происходит задержка: API > очередь > MES > CRM > оператор > доставка;
* насколько быстро и надёжно система обрабатывает внешние и внутренние запросы;
* когда нагрузка начинает превышать возможности инфраструктуры;
* сколько заказов застревает в очередях или не обрабатывается.

**Мониторинг необходим, чтобы:**

1. **Предотвращать простои и инциденты**, а не реагировать на жалобы пользователей.
2. **Снижать финансовые потери**: невыполненные API‑заказы приводят к прямым потерям контрактов.
3. **Улучшать производительность производства**: операторы тратят время на ожидание загрузки страницы, что снижает throughput.
4. **Увеличивать доверие B2B‑партнёров**, которым критична предсказуемость.
5. **Повышать прозрачность процессов**: можно видеть, где возникает узкое место и ранжировать инициативы по их устранению.

Мониторинг - это фундамент, без которого невозможно решить текущие проблемы в компании и контролировать рост нагрузки. Он позволяет бизнесу принимать обоснованные решения и быть уверенным в стабильности сервиса.

---

## 2. Выбор подхода к мониторингу

В разных подсистемах компании требуются разные уровни наблюдаемости. Поэтому планируется использовать комбинацию трёх подходов:

### "Четыре золотых сигнала"

Подходит для:
* Онлайн‑магазина,
* CRM,
* MES (web‑часть),
* API для партнёров.

Эти компоненты важны с точки зрения внешнего потребителя: нужно понимать скорость, надёжность и загруженность.

### RED (Rate, Errors, Duration)

Подходит для:

* сервисов расчёта стоимости,
* RabbitMQ‑консьюмеров,
* сервисов обработки заказов.

RED идеально показывает состояние системы, которая обрабатывает фоновые задачи.

### USE (Utilization, Saturation, Errors)

Подходит для:

* инфраструктуры (БД, RabbitMQ, файловое хранилище),
* сетевых ресурсов, очередей,
* CPU/GPU расчётных мощностей.

USE поможет вовремя найти узкие места при росте нагрузки.

* оценивать KPI операторов и продавцов;
* замечать отклонения и прогнозировать необходимость масштабирования.

## 4. Итог

Предложенный мониторинг закрывает все слабые места текущей системы: очереди, API‑партнёров, расчёты стоимости, работу операторов, CRM и онлайн‑магазин. Бизнес получает полный контроль над жизненным циклом заказа и прозрачность SLA.

По итогам внедрения можно будет:

* видеть узкие места;
* предотвращать инциденты до жалоб;
* обоснованно масштабировать систему;
* выполнять обязательства перед партнёрами и клиентами.

Готов продолжить: разработать архитектуру мониторинга (Prometheus + Grafana + Loki/ELK + OTel), схемы дашбордов и план внедрения по спринтам.

## План действий

1. **Развернуть time‑series базу и стек мониторинга**

    * Поднять Prometheus в отдельном инстансе.
    * Настроить retention 15–30 дней.
    * Настроить Alertmanager.
    * Развернуть Grafana.

2. **Подключить сервисы к сбору метрик**

    * Добавить Prometheus endpoint в Spring Boot и C# сервисы.
    * Настроить экспортеры RabbitMQ.
    * Настроить node_exporter на всех EC2.
    * Добавить cloud exporter для Yandex DB, S3.

3. **Настроить распределённые трассировки**

    * Внедрить OpenTelemetry SDK во все три приложения.
    * Проброс trace‑id через RabbitMQ.

4. **Определить и создать дашборды**

    * Dashboard API (общий).
    * Dashboard RabbitMQ.
    * Dashboard DB.
    * Dashboard бизнес‑метрик (conversions, order funnel).

5. **Настроить SLA/SLO/SLI**

    * Для магазина: latency < 300 ms, error rate < 1%.
    * Для CRM: error rate < 0.5%.
    * Для MES API: latency P95 < 3 min.

6. **Настроить оповещения**

    * Slack / Email / PagerDuty.
    * Инцидент‑менеджмент.

7. **Написать документацию для команды**

    * Регламент по реакции на алерты.
    * Плейбуки.

## Показатели насыщенности (saturation)

### 1. CPU > 80% на API более 5 минут

* *Почему:* выше 80% растёт latency и вероятность ошибок.
* *Реакция:*

    * Авто‑алерт.
    * DevOps проверяет - масштабирование: добавить инстанс / поднять тип машины.

### 2. Количество сообщений в очереди MES > 5000

* *Почему:* это означает, что система не успевает обрабатывать расчёты стоимости.
* *Реакция:*

    * Включить auto‑scaling потребителей.
    * Проверить DLQ.
    * Создать тикет разработчикам.

### 3. Latency MES API > P95 10 минут

* *Почему:* это критический UX‑провал для партнёров.
* *Реакция:*

    * Создать инцидент.
    * Уведомить партнёров.
    * Авто‑рестарт обработчиков.

### 4. DB connections > 80% лимита

* *Почему:* база перестанет принимать подключения.
* *Реакция:*

    * Авто‑алерт.
    * Проверка пула соединений.
    * Плановое увеличение инстанса.

### 5. DLQ > 10 сообщений за 5 минут

* *Почему:* означает постоянную ошибку в логике.
* *Реакция:*

    * Создать баг‑тикет.
    * Срочная диагностика.

### 6. Размер S3 растёт > 20% в месяц

* *Почему:* вероятно левая загрузка файлов.
* *Реакция:*

    * Алерт.
    * Проверка файлов.
    * Очищение орфанных моделей.

## Что должно происходить при превышении порогов

* Автоматическое создание инцидента.
* Уведомление в Slack/Email.
* В критических случаях - автоматическая "звонилка" менеджерам.
* Генерация тикета в Jira.
* Запуск автоматических плейбуков - рестарт сервисов, увеличение числа потребителей.
