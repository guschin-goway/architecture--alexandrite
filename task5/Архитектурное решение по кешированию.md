# Архитектурное решение по кешированию

---

## 1. Мотивация

Проблема: операторы MES жалуются на долгое время загрузки первой страницы. Ранее показ всех заказов тормозил, команда ввела фильтр по статусам и пагинацию - не помогло. Причины:
* запросы к основной БД дают тяжёлые агрегации (группировки по статусам, сортировки по времени);
* однин инстанс приложения и БД - узкие места;
* высокий входящий поток заказов (включая API партнёров).

Цели кеширования:

1. Быстро отдавать "последние N заказов" и агрегированные по статусам счётчики (операторам нужна свежая информация в реальном времени для взятия задач).
2. Уменьшить нагрузку на основную БД.
3. Обеспечить предсказуемое время отклика дашбордов и API просмотра заказов для CRM/операторов.
4. Сохранить консистентность бизнес‑логики и дать приемлемую свежесть данных (SLA на latency для "новых заказов").

Кандидаты для кеширования:

* **Read‑путь для дашборда MES:** последние заказы, агрегированные значения по статусам;
* **Часто читаемые сущности:** order summary (id, status, created_at, price, operator_id);
* **Результаты тяжёлых вычислений:** промежуточные результаты расчёта стоимости.

## 2. Предлагаемое решение - общий обзор

Решение сочетает **серверное кеширование** (in‑memory cache + read‑optimized store) и **кеш на уровне браузера (client cache)** для нечасто меняющихся данных.

### Почему серверное + read-store?

* Операторам нужна низкая latency и свежие "последние" заказы: серверный кеш (Redis/InMemory) даёт ответы за миллисекунды.
* Клиентское кеширование полезно для статических справочников (partner metadata), но не решит проблему горячего read‑path дашборда.
* Read‑optimized store (например, Redis + sorted sets / materialized views в отдельной базе ) позволит быстро отдавать списки и агрегации.

### Компоненты решения
1. **Primary DB** - источник правды.
2. **Cache layer (Redis cluster)** - in‑memory хранилище.
3. **Read store (Elasticsearch / ClickHouse / Postgres materialized views)** - для полнотекстного поиска и аналитики для сложных фильтров и исторических данных.
4. **MES backend (workers + API)** - логика чтения сначала из cache (cache‑aside), fallback в DB / read-store.
5. **Client (browser)** - легкий cache для metadata.

## 3. Паттерн кеширования

### Выбранный паттерн: **Cache‑Aside (Lazy Loading)**

**Почему:**

* Позволяет держать кэш в актуальном состоянии без блокирующих операций записи в критической path.
* При чтении: сервер сначала пытается получить данные из кеша; если нет - читает из DB, записывает в кеш и отдает клиенту.
* Обновление кеша: при изменении статуса/создании заказа через backend публикуется событие в RabbitMQ; consumer (cache invalidation service) обновляет ключи/счётчики в Redis.

**Почему не Write‑Through / Write‑Behind:**

* Write‑Through (синхронная запись в кеш при каждом write) гарантирует, что кэш всегда актуален, но добавляет задержку в write path (каждая запись выносится на запись в Redis) - риск ухудшения throughput при пиковых нагрузках. Кроме того, при сбое кеша операция записи потенциально блокируется/ошибается.
* Write‑Behind (asynchronous write-back) рискован при сбоях - возможна потеря данных, и сложнее достигнуть консистентности между DB и cache.

**Почему не Refresh‑Ahead:**
* Refresh‑Ahead периодически обновляет кэш заранее; у нас рабочая нагрузка и потоковые события динамичны (API партнёры шлют много заказов). Refresh‑Ahead может приводить к ненужным обновлениям и большему ресурсу.

Итого: **Cache‑Aside + Event-driven cache updates** - лучшее соотношение свежести, производительности и простоты реализации.

## 5. Стратегия инвалидации кеша

### Комбинированная стратегия: **по ключу (event-driven) + TTL (time‑based fallback)**


**Почему такая стратегия:**

* Event-driven даёт почти real-time обновления и минимизирует расхождение между БД и кешем.
* TTL предотвращает бессрочное расхождение.
* Программная инвалидация (через событие) позволяет точечно обновлять только необходимые ключи - экономит ресурсы.

**Почему не только TTL:**
* TTL‑только приведёт к заметному устареванию данных.
